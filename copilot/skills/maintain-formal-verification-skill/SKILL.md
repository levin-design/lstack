# 维护形式化验证技能

形式化检查证明的是它所描述之物的性质。当代码改变而验证不变时，检查可能一直通过，却在描述已经不存在的代码。这种通过是危险情形，因为它看起来像证明。本技能是 `/create-formal-verification-skill` 生成的验证技能、或任何针对具名代码运行模型检查器、证明器或代码级验证器的项目本地技能的维护循环。项目本地技能处理 agent 在使用该技能期间所做的改动。本技能处理跳过它的改动：合并、未经该技能所做的编辑，以及跨多个提交累积的漂移。

## 结果

给每个检查一个结果，并说明是哪一种：

- **in sync**：自上次同步以来没有改动改变检查所描述的内容，且检查通过。
- **updated**：代码已改变，验证现在描述新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码破坏了该性质。这是关于代码的发现，不是漂移。
- **blocked**：检查无法重新对齐或无法运行。准确说明原因。

一个检查可以同时是 updated 和 bug：更新让验证重新描述代码，然后该性质在其上失败。

## 编辑范围

只编辑验证：模型、harness、性质文件和验证技能本身。运行期间绝不编辑产品代码，除非用户要求。当某性质在当前代码上失败时，不要削弱该性质或模型来让它通过。报告失败。

## 一轮流程

1. **找到检查。** 验证技能没有固定名称，因此按它做什么来找：一个针对具名代码运行模型检查器、证明器或其他验证器的项目技能。读取你找到的每一个，或用户指定的那一个。对于每个检查，收集：性质、它覆盖的代码、边界与假设、运行它的命令，以及最后一次确认它描述该代码的提交。如果不存在验证技能，停止并指向 `/create-formal-verification-skill`。如果技能没有记录同步提交，使用最后一个改动验证文件的提交，并说明你是这样做的。

2. **按原样运行。** 在改动任何东西之前，先把每个检查运行一次，并记录结果。这里的通过并不说明代码正确，只说明旧描述仍然成立。这里的失败可能是漂移，也可能是 bug。在第 5 步之前不要下结论。

3. **阅读被覆盖代码的每一处改动。** 对被覆盖文件从同步提交到当前提交做 diff，并阅读每条提交信息。还要寻找移动过的代码：被覆盖的函数即使重命名、拆分或移到另一个文件，仍属被覆盖代码。还要寻找触及检查所守护状态的新代码，例如写入相同字段的新函数。对每处改动，判断它属于以下哪种：
   - **无影响。** 该改动不改变验证所描述的任何内容，例如格式化、注释，或验证未覆盖的代码路径。要对照模型或 harness 检查这一点，而不是对照提交信息。
   - **验证不再描述该代码。** 原本一个不可分割的动作现在变成两个，新增或删除了分支，检查移动了位置，新路径到达了受守护状态，或某个值的范围改变了。模型或 harness 必须更改。
   - **承诺被有意改变。** 该改动改变了代码所承诺的内容，且改动中的证据表明这是有意的：文档注释、测试、变更日志或提交信息。性质必须更改，且你必须引用该证据。
   - **承诺可能已被破坏。** 代码改变了，且没有证据表明承诺被改变。将随后的失败视为 bug 候选。

4. **依据代码更新，而不是依据结果更新。** 更改模型或 harness，使每个改动的部分重新指向审阅者可以打开的代码，并让代码中的一个不可分割步骤在验证中也是一个步骤。在重新运行之前依据代码写出更新，不要按“让检查通过”的方式来塑造它。只对有意改变的承诺更改性质。写下旧措辞、新措辞和证据。保留边界，除非改动使它们出错。如果必须减小某个边界，在报告中说明。

5. **重新运行并判断每个结果。**
   - **通过：** 检查可能是在一个已经失去失败能力的描述上通过的。按该性质所防范的方式破坏新代码，例如删除某个新检查或重排某个新步骤，确认检查能抓到它。然后撤销这次破坏。
   - **失败：** 在真实代码上一步步重放反例。如果某个步骤在代码中不可能发生，则是验证有错。修复验证，并说明错在哪里。如果每一步都可能发生，那就是 bug。指出引入它的提交，用代码自己的语言把反例讲成一系列步骤，并用一句话说明危害。如果针对真实代码的廉价测试或复现能显示该 bug，把它作为证据加入报告。不要把它提交到产品代码中。

6. **更新验证技能。** 更新每个检查所覆盖的代码、命令、边界、假设和同步提交。把同步提交设为你所检查的那个提交。对于 blocked 的检查，不要移动同步提交，并在报告中说明。然后像下一个 agent 那样把验证技能走一遍，以确认其步骤仍能运行。

## 报告

对每个检查，告诉用户：

- 结果，以及你阅读过的提交；
- 验证中改了什么以及为什么，每个改动附简短理由：代码形态变了，或承诺被有意改变（附证据）；
- 重新运行的结果，以及你用来证明更新后的检查仍能失败的那次破坏；
- 每个 bug，用平实语言：以代码自己的语言把反例讲成步骤、危害，以及引入它的提交；
- 验证仍未覆盖的内容，包括它本应覆盖却没有覆盖的新代码。

明确说出哪些失败是验证的漂移，哪些是代码的 bug。对于更新前通过、更新后失败的检查，说明旧的通过是基于过时的描述。

把验证更新放在单独的改动中，与任何产品修复分开。
