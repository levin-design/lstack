# 架构设计

用 `not implemented` 空体和伪代码草拟类型、函数签名、类形状和模块边界。综合多个模型视角，然后按选定的草图填充代码。

## 开始

开始前打开一个待办清单，每个阶段一条。

1. 打好基础
2. 草拟设计
3. 达成一致
4. 实现
5. 废弃

## <a id="phase-a-ground-the-problem"></a>阶段 A：打好问题基础

为新代码触及的每个系统建立真正的心智模型。对相关子系统运行 **how** 技能。说出一个文件名不算打好基础。产出 `how` 规定的架构解释。如果设计重新定义了归属或分层，还要对现有形态运行 **why** 技能，让理由成为约束，而不是猜测。

只有当工作确实是没有任何周边系统需要集成的全新项目（greenfield）时，才跳过阶段 A。

## 阶段 B：草拟设计

以设计草图任务和阶段 A 的基础产物运行 **arena** 技能。把 `references/runner-prompt.md` 作为每个运行器的提示词传入。

运行器取自 `.github/skills/lstack/references/lstack-models.md` 中的 `architect runners` 行，代替 `arena runners` 行。当它没有记录已确认的标签时，省略 `model`，让每个运行器继承父模型。模型处理遵循 **arena** 技能阶段 A 中的运行器规则。

设计两遍。综合之前至少要有两个结构上截然不同的候选，即使第一个看起来已经足够。这是把 **exhaust-the-design-space** 原则技能落到实处。要整体形态的替代方案，而不是同一形态内的局部修补。

综合之前，用 [`references/design-red-flags.md`](references/design-red-flags.md) 筛查每个候选。假设下一位贡献者是代理，它只看到自己打开过的文件，复制最近的示例，并走能编译的最短路径。优先选择那种「从单个文件看正确的改动，对整个仓库也正确」的设计。

在接口深度上比较可行的候选。优先选择把更多复杂度藏在更小、更简单的公共表面之后的设计。丰富的接口可以通过集中能力而非把能力分散到各层来保持调用链短。

Arena 返回一个综合后的设计包。它的综合决策填入理由文档的「综合决策」一节。

## 阶段 C：达成一致（可选）

默认：带着综合后的设计直接进入实现。没有人工检查点。

当调用者明确要求时才启用检查点：「/architect with checkpoint」「实现前停下来给我看」或类似说法。然后呈现综合后的设计并暂停等待确认。

无论如何，综合结果都可以作为独立提交交付，即 **foundational-thinking** 原则技能的「先搭脚手架」模式。填充期间的破坏只要是有计划、有范围的就没问题，依据 **outcome-oriented-execution** 原则技能。若想在实现前对设计施加对抗性压力，对综合后的草图运行 **interrogate** 技能。

如果人类对形态提出异议（在检查点中或事后），把这当作阶段 A 的证据。在写更多代码之前重新打好基础并重跑阶段 B。

## 阶段 D：按草图实现

用代码替换 `not implemented` 空体，用逻辑替换伪代码。综合后的草图就是契约。偏离它是需要主动暴露的信号，而不是要默默吸收的摩擦。如果某个函数需要草图未预料到的参数，问一问：是草图错了、需求被遗漏了，还是实现越界了。

## 阶段 E：架构错误时废弃

如果实现不断产生草图无法吸收的摩擦，就把草图扔掉。不要往错误的设计上硬拧修补，依据 **redesign-from-first-principles** 和 **fix-root-causes** 原则技能。

信号是*模式*，而不是单个实例。征兆：

- 同一种形态的变通做法在互不相关的代码中反复出现。
- 多个互不相关的边缘情况都需要特殊分支。
- 类型需要逃生舱（`any`、类型断言、在实践中总会被设置的可选字段）才能编译。
- 当草图说状态不是共享的，却出现「我们需要一把锁」的条件反射。
- 调用方必须了解抽象的内部规则才能使用它。
- 实现中出现两个或更多相互独立的、形态相同的阶段 D 偏离。

运用判断力。几个边缘情况并不足以否定一个架构。有些问题本身就复杂。数据中的复杂不等于设计中的复杂。

当你废弃时：

1. 对已构建的内容重跑 **how** 技能。
2. 把新约束当作第一天的假设重新设计，依据 redesign-from-first-principles。
3. 先做减法再做加法，依据 **subtract-before-you-add** 原则技能。新草图在增长之前应当比旧草图更小。
4. 回到阶段 B 重跑 arena。

## 产出

先写调用方的用法，再从中推导类型草图。小改动用一个文件包含新类型和签名。较大的工作给出模块图加类型定义。理由文档随附交付，按 `references/rationale-template.md` 塑形，包含用法草图和综合决策。
