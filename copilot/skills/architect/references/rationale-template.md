# 理由模板

随类型草图一起交付的说明文字。一页。标题使用句首大写，不要套话。用实际内容替换斜体提示。

## 问题

*一段。我们想做什么，以及现有系统或约束中的什么使这个形态变得不明显。如果[阶段 A](../SKILL.md#phase-a-ground-the-problem) 暴露出设计必须遵守的约束（需要互操作的现有类型、不能破坏的调用方、跨越我们边界的不变量），在这里点名，让读者看到你所看到的相同约束。*

## 用法（调用方视角）

*先写这一节，在类型草图之前。展示消费者会读的 README 或快速开始，外加他们自己代码中两三个真实的调用点。他们导入什么、调用什么、返回什么。[结构](#shape)中的类型草图由它推导而来。两者必须一致。当它们分歧时，让草图对齐用法，而不是反过来。调用方的体验就是规格。类型服务于它。*

## <a id="shape"></a>结构

*推荐的架构。先数据结构。然后数据如何流经签名。点名承重的决策。说明哪些不变量编码在类型中、校验位于何处，以及系统刻意不做什么。明确评判接口深度。说明公共表面隐藏了什么复杂度、哪些仍暴露给调用方，以及为什么接口没有再大一点的必要。为每个决策引用背后的原则（例如 `per boundary-discipline`）。不要复述原则。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填入。记录哪个候选成为基础及原因、从其他每个候选中借鉴了什么、拒绝了什么及原因。*

## 接受的权衡

*选定的形态所做的每个权衡一条。形式：「我们接受 X，以换取 Y」。点名任何未来读者可能误认为疏忽的内容，包括看起来像过早优化或过早简化的东西。*

## 考虑过的替代方案

*必填。点名至少一个具体的替代形态，用一行说明它为什么落选。就接口深度评判每个替代方案，而不只是实现简单性。点名它暴露给调用方的复杂度和它隐藏的复杂度。当设计空间有真正的竞争者时，这里应有两三个替代方案。当约束强制了答案时，一个就够了，并把结论表述为「这是唯一可行的形态，因为……」。避免罗列同一形态的不同变体。这一节涵盖选定形态考虑并拒绝的设计替代方案，而不是其他运行器候选。*

## 未决问题与风险

*你在草拟期间注意到的、需要人类权衡的事情，以及实现开始前值得标记的风险。以问题的形式表述，而不是断言，这样人类的回答就是解决方案，而不是评论。*

## 下一步实现

*针对草图首先要构建的东西。一句话。综合之后（或如果启用了检查点，则在阶段 D 签核之后）你会立即开始写的内容。*
