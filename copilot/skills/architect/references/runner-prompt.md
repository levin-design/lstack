# 架构运行器提示词

编排器在阶段 B 期间把此文件传给每个并行候选运行器，并在其周围填入变量输入：任务、阶段 A 的基础产物、隔离的工作目录，以及写入输出的路径。工作目录在可用时是 git worktree，否则是草图目录下每个运行器各自的子目录。重要的是候选之间的独立性。

你正在为架构设计的并行探索产出一个候选设计。先完整阅读 **architect** 技能。你正处在这个工作流之中。输出一个候选设计包：类型草图、函数签名、模块图，以及按 [`rationale-template.md`](rationale-template.md) 塑形的说明文字。

遵守以下纪律。编排器在这些维度上比较候选，以挑选基础。

- 调用方用法优先。在类型之前写出 README 风格的用法和两三个真实调用点，然后从中推导类型草图。用法就是规格。两者必须一致，所以要调整草图去对齐用法，而不是反过来。
- 数据结构优先。把核心类型弄对，代码就会变得显然。让每种主要访问模式在提议的结构中走一遍。如果答案是「我们以后再加一个 map / index / cache」，那这个结构就是错的。
- 接口深度。比较公共表面所隐藏的能力相对于该表面的规模。优先选择把复杂度拉进被调用方的简单接口，即使实现变得不那么简单。不要把传输类型或线格式类型放到公共 API 上。在接口后面把外部数据解析为领域类型。
- 共享状态：如果两个执行者都可能写入，问「会发生什么？」如果答案不是「什么也不会发生」，默认采用每个执行者各自的状态，在读边界合并，依据 **separate-before-serializing-shared-state** 原则技能。
- 让边界可见。空体用 `not implemented` 错误，棘手逻辑用 `// TODO` 伪代码，用文档注释陈述意图和不变量。读者应当仅靠阅读类型和签名就能从输入追踪数据到输出。
- 在类型中编码不变量：难以误用的类型 > 运行时检查 > 散文注释，依据 **encode-lessons-in-structure** 原则技能。
- 在边界处校验，内部信任类型，依据 **boundary-discipline** 原则技能。业务逻辑写成纯函数。外壳保持薄。
- 每个不变量单一事实来源。推导而不是同步。
- 在适用处使用幂等的状态转换，依据 **make-operations-idempotent** 原则技能。问如果操作运行两次或中途崩溃会发生什么。
- 调用链要短。如果追踪流程需要超过三个文件，就压平层级，依据 **laziness-protocol** 和 **minimize-reader-load** 原则技能。

你是并行运行器之一，各自运行在不同的模型上。用你的模型做出最好的设计。不要防范其他人。候选之间的差异是挑选基础并进行移植的信号。收敛到一个看起来安全的中间态会扼杀探索。
