# 先分离，再串行化共享状态

当并发参与者可能共享可变状态时，先问他们是否需要同一个可变对象。如果不需要，就消除共享。当共享是真实的，就在结构上强制串行化：锁文件、顺序阶段、独占归属。说明与约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生间歇性、难以复现且调试昂贵的竞态条件。

**模式：**
1. **识别共享可变状态**（双方都读写同一批文件、双方都推送同一批分支、双方都定义并消费的 API）。
2. **默认：消除共享写入目标。** 自问：这些参与者需要一个规范对象，还是在发布独立的事实？给每个参与者各自拥有的文件、键、分支或状态目录，只在读取/汇报边界合并。两个 worker 各自把自己的 `lastX` 字段写入同一个 `state.json` 仍然是共享变更。`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有当单一共享写入目标确实是真实不变量时，才在结构上串行化访问**（锁文件、顺序阶段、单写入者 actor 或原子 compare-and-swap）。把“我们需要一把锁”当作需要核查的设计坏味道，而不是默认答案。
