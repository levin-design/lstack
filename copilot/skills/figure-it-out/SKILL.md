# 自行设计方法

当任务没有匹配的剧本时，就设计一套。在写任何代码之前，交付物就是工作流本身：一组按任务规模调整严谨程度的阶段，运行科学方法，并留下人类离开后仍可审计的决策轨迹。

## 开始

创建一个待办清单，第一项是阅读 **poteto-mode** 技能的 Principles 小节。然后把下面的阶段作为待办加入。

## 阶段 A：框定

先打好基础，再投入。在你能说出以下内容之前，不要开始运行：

- 完成定义，形式为可证伪的谓词（**prove-it-works** 原则技能）。
- 范围，量化说明：粗略的单元和投入，加上基础调研暴露出的阻塞。
- 严谨程度，宁可偏高。单向门和高爆炸半径需要更多严谨；可逆、低风险的步骤可以少一些。严谨体现为关卡和产物，而不是“更努力试试”。

在投入长时间运行之前，先呈现框定结果和权衡。可逆的工作直接推进（**never-block-on-the-human** 原则技能），但数小时的运行值得设置一个检查点。

## 阶段 B：设计工作流

分解为原子的、可独立落地的单元。按“最未知的风险优先”排序。脚手架和验证先于功能（**foundational-thinking** 原则技能）。

- 在工作之前构建验证 harness，并从改动前状态捕获基线，这样检查读起来就是“旧值 vs 新值”。
- 对于单向门式的设计决策，运行 **architect** 技能（它会运行 **arena**）。对于形态已经明确的机械性工作，跳过它。对已定设计再搞第二轮 arena 属于过度工程（**laziness-protocol** 原则技能）。
- 决定哪些工作扇出。只在接缝处并行，并给每个 worker 独立的工作树或分支（**separate-before-serializing-shared-state** 原则技能）。不要过度扇出。
- 把设计好的阶段列表写下来。这份列表就是人类审阅的对象。

然后执行设计。把它的步骤作为具体条目加入待办清单中阶段 C 与阶段 D 条目之间。每个步骤都在阶段 C 的循环纪律下运行，并把阶段 D 的日志贯穿其中——每落地一步就记一行，而不是把整条轨迹留到最后。

## 阶段 C：运行循环

每个单元都是一次实验。陈述假设，做最小的改动，在真实产物上对照谓词进行测量；有进展就保留，没有就回滚。应用 **sequence-verifiable-units** 原则技能：在开始下一个单元之前先验证当前单元，而不是在最后批量检查。

- 通过检查产物来验证，绝不依赖自我报告。当某事物过于轻松地通过时，先怀疑观察方法，再怀疑系统。
- 为委派的工作配一个评判者。若 worker 钻了关卡的空子，重置并加固契约。若关卡本身有错，用单独的改动修复关卡，而不是绕过它。
- 裁决为 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE。无结论不等于通过。不要隐藏负面结果。

## 阶段 D：保留审计轨迹

通过 **show-me-your-work** 技能记录本次运行。figure-it-out 的工作通常足够宏大，值得提交轨迹，让审阅者能在 PR 中读到它。轨迹加上 diff，才能让人类回来时信任这项工作。

## 阶段 E：验证并交回

在真实产品上对照阶段 A 的谓词检查整体，而不只是检查 harness。把任何反复出现的纠正固化为关卡、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的剧本、严谨程度及理由、决策轨迹路径、已对照谓词验证的内容，以及仍未决的内容。
