# 把我自动化

一套引导流程，把用户的工作约定转成 agent 会遵循的技能。产出是一个为他们量身定制的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

本技能编排另外三项内容：一次内联挖掘（见第 1 步）、`../poteto-mode/playbooks/authoring-a-skill.md` 中的编写规则加上 lstack 总纲 `SKILL.md` 中的格式，以及 **unslop** 技能（行文纪律）。它负责排序。它不替代它们。

## 流程

### 0. 检查是否已有技能

递归查找匹配用户 handle 的 `.github/skills/**/*-mode/SKILL.md` 和 `~/.copilot/skills/*-mode/SKILL.md`。mode 技能可以放在个人分类目录中（`.github/skills/<handle>/`），不只在顶层。如果已存在，用 `vscode_askQuestions` 确认意图（除非他们已说过“更新我的技能”之类的话）：

- 更新现有技能（重复运行的默认选项）
- 从零开始（少见，动手前先问原因）

更新模式会改变流程其余部分：
- 第 1 步只挖掘该技能上次编辑以来的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是哪里变了或缺了什么，而不是从零要捕获什么。
- 第 4 步就地编辑现有文件。保留用户未否定的章节。用新证据修订章节。只为真正的新规则添加新章节。

### 1. 挖掘他们的历史

在分派之前，先定位本会话的 Copilot 调试日志文件夹。环境在可用时通过 `VSCODE_TARGET_SESSION_LOG` 命名它，位于 `~/.vscode-server/data/User/workspaceStorage/<id>/GitHub.copilot-chat/debug-logs/` 下。只使用该范围，绝不扫描其他工作区的文件夹。没有可用日志时，请用户提供会话摘要。

在该范围内梳理最近的 agent 对话，寻找重复出现的模式。把历史切片后并行运行多个子代理（例如最近 2 到 4 周，切成 3 片，让每片都有足够素材）。每个切片挖掘子代理读取父代理提供的工作区范围路径下的日志，寻找下列信号，并返回一份简短的结构化模式清单，附带证据位置。默认值得追查的信号：

- 回复偏好（长度、语气、格式、把话讲浅的纠正）
- 委派习惯（子代理、模型、专用工作流、并行度）
- 验证姿态（“完成”意味着什么、单元测试 vs 实机复现、评审者）
- 代码与行文纪律（风格、引用的原则、lint/format 工具）
- 流程约定（worktree、提交、PR、评审/合并工具）
- 元偏好（任务中途修技能、提议新技能）

在提升某个信号之前，跨切片交叉核对。在 2 个及以上切片中出现的模式置信度高。孤立信号很弱，通常会被丢弃。

### 2. 直接问用户

挖掘会漏掉尚未出现过的意图。使用 `vscode_askQuestions` 工具（结构化多选），而不是让用户从零打字。

形态：一到两个问题，每个 4 到 6 个选项，分类问题设 `allow_multiple: true`。先问宽泛的（“哪些方面最重要？”），再就选中的方面追问具体选项。结构化轮次之后，用一次自由聊天提问来捕获选项没覆盖到的内容。

不要一口气抛 20 个问题。

### 3. 聚类发现

把汇总的信号分组为章节。常见章节（只用手头适用的）：

- **回复风格**：长度、语气、格式。
- **自主性**：不询问就做多少事、MCP 工具使用。
- **先理解**：界定或调查改动时该动用哪些技能。
- **子代理**：默认设置、并行度、模型与任务的对应、专用工作流。
- **行文 / 代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证技能、实机测试工具。
- **流程**：git worktree、提交、PR、评审/合并工具。
- **技能**：技能编写习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了形态。读它了解粒度。不要照抄它的内容。用户的规则与 poteto-mode 的规则并不相同。

### 4. 起草技能

使用 `../poteto-mode/playbooks/authoring-a-skill.md` 中的编写规则，以及 lstack 总纲 `SKILL.md` 中的格式。放置位置：

- 路径：保留现有 mode 技能的分类。对于新 mode，如果仓库已为该 handle 建立了个人分类，用 `.github/skills/<handle>/<handle>-mode/SKILL.md`；否则默认用项目内的 `.github/skills/<handle>-mode/SKILL.md`（或用户偏好个人技能时用 `~/.copilot/skills/<handle>-mode/`）。
- Handle：用户的名字或自选标识。
- Frontmatter `description`：以他们的名字 + `/<handle>-mode` + “按他们的风格工作”触发，而不是用“写代码”“评审 PR”这类通用关键词。
- Frontmatter 格式：遵循 lstack 总纲 `SKILL.md` 的 YAML 规则。让 `description` 保持为一个 YAML 标量。需要标点或折行时，给它加引号，或用 `description: >-` 加缩进续行。
- Frontmatter 默认 `disable-model-invocation: true`。仅当用户明确希望其 mode 在每一轮都生效时才取消。

### 5. 反复打磨行文

对每一行都应用 **unslop** 技能和编写规则。

把草稿给用户看并听取反馈。要预期多轮迭代。狠心删减。mode 技能不是说明书。

### 6. 落地

在基于 main 的 worktree 中工作。提交并开 PR。不要直接推到 main。

## 防护栏

- **不要对单次对话过拟合。** 一次说过、另一次又被否定的偏好是噪声。要多次出现才可固化。
- **不要耍聪明。** 复述其他技能的内容、臆造比喻，或为 agent 读者写“诗意”文字，是有成本无收益。保持可操作。
- **引用，不要内联。** 用户依赖的其他技能应以路径引用出现，而不是粘贴摘录。他们在别处维护的原则文档同理。
- **章节保持最少。** 只有当用户在该方面有具体且非默认的规则时才加章节。“清晰沟通”不算一个章节。“短段落。比较选项时用表格。仅当条目真正并列时才用项目符号。”才算。
- **命名约定保持通用。** 祈使句里用“用户”或“人”，不要用作者的名字。
- **不要强求对称。** 如果用户没有值得写下的流程规则，就整节跳过流程。

## 评估

`-mode` 技能是主观产出。草稿/测试/迭代的基准循环在这里没用。与用户做感觉检查：读起来像他们吗？漏了什么吗？然后发布。

只有当技能的触发准确率在实践中确有问题时，才运行 description 优化循环。

## 何时不要使用

- 用户想要任务专属技能（而非工作约定）：只用编写手册，不需要挖掘。
- 用户想捕获某个狭窄工作流（例如“我如何写提交信息”）。那是普通技能，不是 mode 技能。
