# 认识论

当证据是历史的、碎片化的、有时还相互矛盾时，如何推理置信度，以及如何告知用户而不把它压平成虚假的确定性。代码展示它做什么，而不是*它为何存在*。『为什么』存在于提交、PR、工单、文档和对话中，而这些都是不完整的、有偏见的，有时还缺失。假装不是这样，只会产出听起来自信却误导用户的猜测。

## 置信度层级

输出中的每个论断都必须属于某一层级。层级决定它所在的章节和措辞。

### 1. 直接（Direct）

一条明确的文本引用回答了问题：作者确实*写下*了说明原因的内容，而不是『代码做了 X，所以作者一定想要 X』。例如，PR 描述『这修复了用户拥有 >1000 个条目时无法分页的 bug』，工单『我们加这个是因为客户 Acme 在其安全评审中提出要求』，代码注释 `// clamp to 100 because the upstream API rejects larger values`，设计文档『我们选择方案 A 而不是方案 B，因为我们需要跨重启的持久化』，或作者的聊天消息『改用这种方法，因为旧方法在测试中不稳定』。

措辞：自信、现在时、带引用。『这存在是因为 X。』

### 2. 支持（Supported）

多条间接证据汇聚到同一结论。没有任何单一来源明确陈述它，但跨来源的模式使其成为可能。例如，PR 标题写着『改进性能』，工单标记为『perf』，且周围的提交都触及同一条热路径。或者随变更添加的若干测试都使用超大输入。或者作者同一周的其他 PR 都提到同一起事故。

措辞：自信但明确表明是推导所得，并逐项引用。『证据强烈指向 X：[具体的证据项]。』

### 3. 推断（Inferred）

对上下文的一种合理解读，但没有明确支撑。它是*你的解释*，而不是记录中的事实。例如，PR 没有说明原因，但错误当时正在生产环境发生（根据事故频道的时间线），且修复很仓促（当天合并），所以它很可能是热修复。或者函数名暗示重试逻辑，其重试次数 3 与代码库其他位置团队的 3 次重试惯例相符。

措辞：留有余地，并明确展示推理链。『鉴于 A 和 B，C 似乎很可能，因为 D。』

### 4. 推测（Speculative）

基于薄弱证据的合理假设，其他解释也同样说得通。值得呈现，因为用户可能知道哪个是对的，但要标记为猜测。例如，『这可能是针对一个后来已被修复的浏览器 bug 的变通方案，但我们没有找到当时的证据』，或『这个阈值可能是为匹配某项 SLA 承诺而选的，但没有任何 SLA 文档提到它』。

措辞：『一种可能性是 X，但我们没有直接证据。』通常放在『竞争性假设』中，与其他可能性并列。

### 5. 未知（Unknown）

你查过了但没能查明。这是一个有效且重要的结果。记录它。

措辞：『我们搜索了 X、Y 和 Z，没有找到关于原因的证据。』要具体说明你搜索了*什么*。『我们没能查明』不如『我们用关键词 A 和 B 搜索了工单跟踪器，扫描了 2023 年以来触及此文件的 6 个 PR，并在仓库中 grep 了匹配该阈值的字符串字面量。都没有出现理由。』有用。

## 措辞指南

**置信度词汇**暗示直接或支持的证据，需要紧邻引用。切勿把它们用于推断："because"、"the reason is"、"was designed to"（声称作者意图）、"fixes" / "addresses" / "solves"（声称变更达成了目标）、"the team decided"（声称发生过集体决策）。

**模糊限定词**表示解释，而非报告。在『我们可以合理推断的内容』中大量使用："appears to"、"seems to"、"likely"、"suggests"、"is consistent with"、"one reading is"、"plausibly"、"may have been"、"the evidence points toward"。

**应避免的词汇：**

- "obviously"。如果显而易见，用户就不会问了
- "clearly"。它几乎总是出现在一个并不清楚的论断之前
- "of course"。同上
- "just"（如 "it's just X for performance"）。带有轻蔑意味，通常掩盖了不确定性
- "I think" / "I believe"。你是在综合证据，而不是给出个人观点。改用 "the evidence suggests"。

## 避免合理化

今天『说得通』的代码，可能是出于已不再适用的理由、或当时就错误的理由而写的。不要给混乱的历史强行附上一个干净的理由。不要假设作者做了『正确』的事，再倒推去证明它。不要假设一致的模式是有意为之，它可能只是复制粘贴。不要把证据的缺失当成缺失的证据（『没人提到安全顾虑，所以它一定不是顾虑』）。

## 谄媚陷阱

用户常常内嵌一个假设：『我们为什么这样做，我猜是为了性能？』不要简单地予以确认。这个猜测是调查的提示，而不是待验证的结论。把它当作众多候选之一，独立核查证据。如果证据支持它，就带引用地说明。如果不支持，也说明，并呈现证据*确实*支持的内容。

## 当证据相互矛盾

在输出中呈现两个来源及引用。不要挑选更符合整洁叙事的那个。例如，工单说『客户 X 的合规要求需要我们做这个』，而 PR 说『清理这一领域的技术债』。两者都可能为真（工单驱动了工作，PR 给出了作者的表述框架），也可能有一个是错的。让用户来判断。

## 当证据缺失

诚实的『我们不知道』是最有价值的输出之一。用户会了解到答案不在显而易见的地方，他们需要问人（原作者、产品负责人、团队负责人），或者他们可以决定这个问题不值得继续追查。不标记缺口，反而用自信的猜测填补它，会主动伤害用户，因为他们会据此行动。具体地命名每个缺口：问题是什么、搜索了哪些来源、在每个来源中搜索了什么、以及你找到了什么（没有，或只有边缘材料）。

## 定稿之前

在综合员交付输出之前，它检查『我们的发现』和『我们可以合理推断的内容』中的每个论断。每个论断要么有引用，要么移到『推断』或『假设』。其措辞与其层级匹配。它不把代码当作其自身意图的证据（如果这样做了，删除或重新分类）。输出中有『我们不知道的内容』一节。如果没有提到任何缺口，那很可疑。要么证据异常完整，要么有什么被掩盖了。
