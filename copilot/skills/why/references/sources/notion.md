# Notion 文档

## 本来源包含什么

- PRD（产品需求文档）
- 技术规格与 RFC
- 架构决策记录（ADR）
- 设计评审的会议记录
- 包含领域背景的团队页面
- 事故复盘
- 可能解释防御性代码的运维手册
- 设定优先级的战略文档

Notion 常常是"为什么"在变成代码之前以长文形式存在的地方。一个重要功能通常有一份文档。

## 如何检索

使用 Notion MCP。

1. **用 `notion-search` 做关键词搜索。** 尝试：
   - 功能名称
   - 目标代码中的关键符号 / 类名
   - 作者的 handle（设计文档常常在代码落地之前就已撰写）
   - 错误字符串或用户可见的术语
   - 如果你知道代码上线时间，可使用带时间范围的查询
2. **用 `notion-fetch` 获取候选页面。** 读全文，而不是预览。理由常常埋在文档中段。
3. **跟踪反向链接与子页面。** 设计文档常常有子页面，用于记录考虑过的替代方案、附录或实现说明。
4. **检查相关数据库。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 可以找出讨论过该决策的会议记录。
5. **搜索作者专属空间。** 如果 PR 作者有个人笔记空间（某些公司很常见），其中可能存有代码之前的探索性思考。

## 这里的良好证据长什么样

- 带有"问题陈述"或"动机"部分、且与目标代码目的相匹配的 PRD
- "考虑过的替代方案"或"被否决的方案"部分
- 明确指出目标代码是某次特定事故修复的复盘文档
- 记录"我们因为 Y 决定 X"、且作者/日期范围与 PR 相符的会议记录
- 非敷衍填写的 ADR 模板（状态、背景、决策、后果）

## 常见陷阱

- **过时文档。** 规格常常在实现之前撰写且不再更新。文档描述的可能是已经改变的方案。要与实际 PR 交叉核对。
- **文档与现实的偏差。** 规格可能说"我们会做 X"，但代码实际做的是 Y。要标记这种分歧。综合者会呈现这一矛盾。
- **模板套话。** 有些组织要求填写"Why"部分，结果被灌入空话。要寻找具体性。
- **未被链接的文档。** 最相关的文档可能没有从任何地方链接过来。广泛的关键词搜索有帮助。
- **多份草稿。** 如果某个主题有多份文档，找到已定稿或最近更新的那份。检查日期。
- **访问受限的页面。** 如果你无法访问某个页面，将其记为缺口。

## 需要返回什么

对每份相关文档：
- 标题与 URL
- 作者与最后更新日期
- 动机文本（逐字引用），附页面/章节位置
- 相关的链接页面（以便综合者引用）
- 文档是已定稿还是草稿
