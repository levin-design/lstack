# 状态图

图表用阅读者自己的语言展示系统如何在状态之间迁移。这位阅读者决定行为是否正确。

## 运行

在仓库之外的临时文件夹中工作。编写 TLA+ 规格及其配置。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，因此请用能够执行 TypeScript 的运行时来运行它。

首次运行会通过 mise 安装 TLC 和 Java，并且需要网络。

## 编写规格

- 把阅读者认可的每条规则写成 INVARIANT。规则可以关于一个屏幕、一个结果、一个存储值或一条消息。如果模型中没有对应某条规则的变量，就添加该变量。绝不要为了让规则成立而削弱规则。
- 把 `Next` 写成各动作的析取，例如 `YouPressPlay \/ YouPressStop`。如果不这样写，TLC 会把每一步都命名为 `Next`。
- 没有出边的状态会破坏 `NoDeadlock`，即使它是一个正确的结束状态也是如此。当某个 INVARIANT 或 PROPERTY 已经使用了该名称时，规则为 `CHECK_DEADLOCK`。在 `Next` 中添加一个仅在结束状态为真且不改变任何东西的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 中为它指定标签。

## 选择图表

需要判断的工作由你完成：每个状态和箭头上的文字、阶段及其颜色、标题，以及给阅读者的报告。把你的工作放在一个视图模块中，并用 `--view` 提供。

为了展示阅读者的语言，视图导出 `state(vars)`。`state()` 返回的值决定形式：

- 字符串给出扁平图表：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象为每个键给出一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用阅读者能看到或关心的内容给每个状态加标签，例如 "Paying" 或 "Lease held, write pending"。标签中不要出现变量名。在 `vars` 中，TLA+ 序列是一个键从 1 开始的对象，所以 `v.pc[1]` 就是 `pc[1]`。集合是数组。

视图还可以导出 `step(action, from, to)`。它接收 TLC 动作名称以及该步骤前后的值，并返回箭头的标签。按用户看到的方式书写每个步骤标签，例如 "you press play" 或 "the connect fails"。不要写出代码或 TLA+ 动作的名称。在图表中结局相同的两个动作得到相同的标签，从而共用一条箭头。

当某一步骤只能在某些条件下发生时，在标签末尾用方括号写出该条件，使用阅读者的语言，例如 `you press play [while the file loads]`。在区域图中，命令会用其他区域标签的语言，把该条件写在该箭头上的其他区域处，例如 `[when Offline]`。你的方括号会替换它，于是从同一状态出发的两条箭头可能看起来相同。所以在区域图中，不要为另一个区域上的条件写方括号。当某个没有任何标签展示的值决定了一步的去向时，在标签中写出结果，例如 "the roster read fails"。

视图还可以导出以下内容：

- `group(vars)` 返回阶段名称。每个图表状态获得其所属组的颜色。当一个图表状态背后的模型状态分属不同组时，该状态不获得颜色。
- `colors` 为每个组名给出一个颜色类。
- `title` 是一个字符串，图表会在顶部显示它。

对每个模型状态，命令最多调用一次 `state()` 和 `group()`；对每个步骤最多调用一次 `step()`。图表和报告都使用这些答案。因此，让每个函数只依赖它的参数。

图表不会绘制停留在同一标签内的步骤。当阅读者必须看到这样的步骤时，拆分标签。

目标大约 20 条箭头或更少，因为更繁忙的图表难以阅读。首先让 `state()` 返回更粗粒度的标签。把行为相同的值归为一个标签，并省略阅读者不需要的细节，例如一个在途调用，其返回不改变任何东西。保留 bug 路径上的每个状态，并保留每个标记。当合并把 `breaks` 状态改成 `mayBreak` 时，它会隐藏规则在哪里被破坏。不要合并两个破坏不同规则的状态，因为那样阅读者就无法看出哪条规则在哪里被破坏。如果图表仍然过于繁忙，对那些阅读者不需要的步骤，从 `step()` 返回 `null`，例如每个状态都有的重置，或者其箭头重复了其他箭头所展示内容的步骤。隐藏步骤时遵守以下规则：

- 保持每个图表状态都能通过箭头从某个起始状态到达。
- 对模型中每个有出边的图表状态，至少保留一条出边箭头。
- 要么隐藏一条箭头的所有步骤，要么一个也不隐藏。只隐藏其中一部分时，它的条件会变窄。
- 在交接说明中，说明图表隐藏了哪些步骤。

## 阅读报告

- 在图表中，破坏规则的状态带有 `breaks` 类。当它背后的模型状态中只有一部分破坏该规则时，它带有 `mayBreak` 类。图例会列出每个标记对应的规则。当两条规则都被破坏时，它会在一个标记上同时列出两条规则，因此在交接说明中要说明哪个状态破坏了哪条规则。在区域图中，当包含它的每种区域状态组合都可能破坏规则时，该状态获得标记。当某个组合可能破坏规则而其中没有任何状态带标记时，该组合中的每个状态都获得标记。
- TLC 会越过破坏规则的状态，所以图表展示的是 bug 之后的状态。
- 由于 TLC 会越过 bug，对其状态没有限制的模型可能无限运行。保持常量较小，或添加 CONSTRAINT。
- 使用 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态计为一个状态，图表绘制那一个状态。箭头可能指向它，而不是该步骤实际到达的状态，报告会说明这一点。
- TLC 会检查 CONSTRAINT 或 ACTION_CONSTRAINT 之后每个状态中的规则，但不会探索该状态或检查其死锁。当 TLC 为某条规则找到的最短路径终止于这样的状态时，图表绘制该状态，报告给出该路径。图表不绘制越过边界后的其他状态。这类状态中的死锁不会显示。TLC 还会检查 ACTION_CONSTRAINT 排除的每个步骤之后的规则，即使它以另一种方式到达了下一个状态。当 TLC 为某条规则找到的最短路径以这样的步骤结束时，图表绘制该步骤。
- 命令按配置原样用 TLC 检查规则，只使用一个工作进程。当某条规则被破坏时，命令移除该规则并再次运行 TLC，直到没有规则被破坏。首次破坏之后，每次运行在 100,000 个不同状态处停止，以免大模型无限运行。当某次运行达到该上限或因错误停止时，报告会在「Rules not checked」下列出未检查的规则，图表不会标记它们。未检查的规则可能成立也可能被破坏。要检查它，请从配置中移除被破坏的规则，或让模型更小。该上限会添加一个改变 TLC 变量顺序的模块，因此对于 PROPERTY，TLC 找到的反例可能与没有该上限的运行不同。
- `tlc.out` 是 TLC 按配置原样打印的内容。当图表未展示某条被破坏规则的 bug 路径时，`tlc-RULE.out` 是 TLC 在找到该规则的运行中打印的内容。当 TLC 重复其第一条警告时，纯 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 在命令读取的输出中省略了第二份。这只在 Java 以 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告是它建议传入该标志，而它只打印一次。

## 展示图表

以 `mermaid` 代码块向用户展示 `chart.mmd`。图表预算为 500 个状态，按配置原样由 TLC 计数。超过该上限时，图表只绘制通往被破坏规则的路径；当没有规则被破坏时，命令不会写出 `chart.mmd`。它仍会检查每条规则，报告会给出状态数和每条 bug 路径。要看到完整图，请让模型更小。

使用 Pele 渲染图表。当用户要求图片，或图表大到无法以文本阅读时，遵循 `references/render.md`。除非用户要求，不要使用其他渲染器。

## 交接

把每个图表及其 Mermaid 文本交给必须做决定的人。为每个 bug 添加一行：规则、阅读者对该规则的一句话描述，以及报告中编号的路径。说明模型省略了什么。给出再次生成文件的命令，并指定新的 `--out` 文件夹。

当模型描述的是代码时，把每条 bug 路径对着真实代码重放，作为测试或实时复现，每个动作一步。如果 bug 没有发生，在证明模型没错之前，先认为模型是错的。
