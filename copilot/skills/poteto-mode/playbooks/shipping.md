### Shipping

**落地内容由你负责。独立验证每个 PR，只从根代理落地已验证的连续段，然后不再插手堆栈。**

1. **解析 forge，然后在落地前独立验证每个 PR。** 所有 PR 操作都使用 GitHub CLI（`gh`）。绝不要求 Graphite（`gt`）。若 `gh` 不可用，停下来并告诉用户该运行哪些命令。每个 PR 一个验证者，每个都是验证者子代理，用匹配的控制技能（如项目自带的 UI 或 CLI 测试装置）以用户的方式运行该改动，对比父级与 head，并在该 PR 上贴 `PASS`、`PASS+NOTES` 或 `FAIL`。只有未编写该代码的代理给出的裁决才算数，因为作者检查的是它本来想构建的东西。CI 全绿和机器人评审通过都不是裁决，因为二者都没有以用户的方式运行该改动。
2. **只落地以底部为根的那一段连续已验证序列。** 从最低的未合并 PR 往上走，在第一个没有 `PASS` 或 `PASS+NOTES` 的 PR 处停下。它下方的 PR 构成该段，顶端那个是上限。未验证 PR 之上的已验证 PR 要等待，因为没有下面的代码它无法落地。若某个 PR 的分支既不包含也不需要那段代码，它可以移到主干上自行落地。但它需要新的裁决，因为旧裁决是在那段代码位于其下方时运行的，而主干没有那段代码。
3. **重新核查裁决是否仍描述当前代码。** 一次裁决覆盖一个补丁，而链式变基会把其上方的每个 PR 移到新 SHA 而不让任何检查失败。在信任旧裁决之前，比较裁决 SHA 与当前 head 的 `git patch-id`。当补丁只在测试、文档或 lint 配置上有差异时，若 lane 运行的对象在两个 SHA 上构建结果相同（除噪声外），则该 lane 的结果仍然成立。噪声是指在裁决 SHA 的两次构建之间也会出现差异，或内嵌的提交 SHA。报告每种噪声及其文件，以便读者核对判断。改动本身仍需新的检查和评审，因为旧裁决从未见过它。没有构建输出的 lane（如开发服务器）无法证明这一点，所以要重跑它，并重新验证任何其他漂移之处。
4. **自底向上，一次一个 PR 地落地。** 始终合并该段中最低的未合并 PR，用 `gh pr merge <pr> --squash`。若某 PR 的基线仍是其父分支，则合并进那个分支，而不是主干。回读 PR 的结果（`gh pr view <pr> --json state,mergedAt,baseRefName`），因为当合并队列只是把 PR 排队时，合并命令可能报告成功，而被请求的自动合并并不等于已合并。已落地的 PR 读作 merged，基线是主干，而不是其父分支。只在裁决覆盖当前 head 的 PR 上启用 `--auto`（GitHub 自动合并），因为它会落地任何就绪的 head。合并落地后，把基线原为被合并分支的那个 PR 重定向到主干（`gh pr edit <pr> --base <trunk>`），把其补丁移到合并结果上，并用 `--force-with-lease` 推送。裁决覆盖的是补丁，不是其提交，因此第 3 步的 patch-id 规则决定裁决是否幸存。检查通过且裁决幸存后合并它。
5. **落地期间不要动堆栈。** 第 4 步对下一个 PR 的移动是对分支或基线的唯一改动，因为合并会落地其分支和基线在那一刻持有的内容，无论有无裁决。用 `playbooks/babysit.md` 中的排队观察者（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）监视该段，直到它在上限处报告 `COMPLETE`。父级合并时基线移到主干是预期行为，不是要修复的损伤。如果合并停滞，先查清原因再改任何东西。
6. **在上限处停止。** 延长该段需要新的裁决，因此那是重新走一遍第 1 步。

**回复：** 已验证的那一段及其上限、每个 PR 的裁决及产出者、落地了什么以及你如何确认、下一处缺口还需要什么。
