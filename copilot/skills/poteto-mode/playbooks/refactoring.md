### Refactoring

**契约由你负责。结构改变，行为不变。** 区别于添加行为的 Feature 和纠正行为的 Bug fix。

如果清理暴露出缺失功能或真实缺陷，把它拆出去，先按钉住的契约发布结构改动。允许重新设计，但要明确说明并路由到 Feature。大型或横切的结构工作属于 **figure-it-out** 技能。本剧本针对聚焦到中等规模的改动。

1. 先钉住行为契约。对受影响子系统跑 **how** 技能以了解契约，然后在任何结构移动之前写一个刻画测试、快照或等价性装置，捕获当前行为。如果该区域没有覆盖，在动结构之前先写钉子。类型检查和 lint 不是钉子。
2. 按 **principle-model-the-domain** 指出代码缺失的结构。当形态已经清晰且局部时，保留无聊的代码。重塑必须删除分支或非法状态，而不是增加间接层。
3. 指出目标形态。说明如果今天重建，模块布局、类型和调用图应该是什么样（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。如果目标跨函数边界，在移动前运行 **architect** 技能对形态做并行设计探索。
4. 先减后加。在引入新形态之前，删除死代码、合并单调用方包装、去掉冗余校验器、移除孤儿引用（**principle-subtract-before-you-add**）。到达目标形态的最小改动才上线（**principle-laziness-protocol**）。"可能有用"的投机清理要回退。
5. 以小步、保持行为的方式移动，每一步都让钉子保持全绿。对 API 重塑，在同一波中迁移每个调用方并删除旧 API（**principle-migrate-callers-then-delete-legacy-apis**）。不要兼容垫片，不要新旧并行的路径。对每个重命名都对照实际文件抽查。重命名会悄悄漏掉字符串、散文和反向引用中的使用。使用配置的 refactoring 模型（模型文件记录了已确认标签时用该标签，否则用父模型）把机械编辑委派给子代理，并给出具体范围（文件路径、被移动的名称、要保持的行为）。按 Subagents 一节为每项工作选择子代理的推理级别以及快速或标准速度。
6. 在真实产物上证明行为未变，而不是"它能编译"（**principle-prove-it-works**）。对较大的重塑，运行等价性检查：一个 diff 新旧输出的脚本、用录制的基线对新代码回放，或通过相关控制技能在匹配界面上做一次冒烟运行。
7. 确认改动值得保留。成功度量是降低读者负担（**principle-minimize-reader-load**）。如果差异没有在任何地方降低读者负担，就回退它。
8. 变基为小的有序提交。一个减法提交，然后是重塑，然后是任何跟随的清理。用 **sequence-verifiable-units** 原则技能塑造它们，使每个保持行为的切片在进入下一个之前保持全绿。执行 **Opening a PR**。

**回复：** 改变了的结构、你用来钉住它的契约、等价性证明、读者负担变化、上线了什么、回退了什么。没有新行为。
