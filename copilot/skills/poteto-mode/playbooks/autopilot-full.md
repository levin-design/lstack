### Autopilot-full

**你负责裁决，永远不负责 PR。每个 PR 由同一个所有者从构建带到合并；在你的 swarm（它从未写过这些代码）证明将要落地的代码之前，什么都不合并。**

一次裁决覆盖一个补丁，CI 全绿覆盖一个 head。第 4 步完整跑一次 swarm，只有重大变更才再跑一次。`playbooks/shipping.md` 中的 patch-id 规则可以沿用一条 lane 的结果，而每个新 head 都需要自己的绿色 CI。

1. **操作者的闸门优先。** 授权只覆盖队列中的条目，因此操作者声明归其所有的条目，以及队列之外的 PR，都止步于 merge-ready。要求说明计划并不等于放行。
2. **每个 PR 派生一个所有者，并让其工作留在接替者能找到的地方。** 整个程序只解析一次 forge。所有 PR 操作都使用 GitHub CLI（`gh`）。绝不要求 Graphite（`gt`）。若 `gh` 不可用，停下来并告诉用户该运行哪些命令。每个所有者都是一个验证者子代理：它负责构建、按 `playbooks/opening-a-pr.md` 开启自己的 PR、在真实产物上证明改动、按 `playbooks/babysit.md` 看护到全绿，并在第 4、5 步通过后合并。

   尽早开启 PR，让 CI 和机器人随工作并行运行。只有在 slop-strip（用 **unslop** 技能做一轮 slop 清理）和 `/no-comments` 通过之后，代码才算就绪，因此完整 swarm 是在完成的代码上运行。然后变基到当前主干，在自证之前报告代码就绪的 head，这样验证运行在补丁最终落地的基线上。之后每个 head 都要报告，自证、CI 和看护完成后报告 merge-ready。修复轮次留在该基线上，除非主干冲突、CI 失败，或同一批文件上有已知的并发改动落地，因为每次变基都会重启 CI。在代码就绪推送之前，以及需要验证者的后续推送之前，在已提交的 head 上对触及路径运行仓库的检查。

   假设 VM 会死。启动后不久就推送，并按 **show-me-your-work** 技能在根代理的存储中（路径见系统提示词）开始决策轨迹，然后在开始下一单元之前推送每个完成的单元。派生某子代理的人要在该存储中记录它的 id、状态，以及过往同类运行的 stuck-after 时长，这样父进程死掉时根代理可以探测它。只对自己拥有的分支强制推送，使用 `--force-with-lease` 并锁定到你最后推送或接管的 SHA；对于任何不是你做的推送，停下来向根代理报告。
3. **所有者从主干并行开工，绝不堆叠，** 这样每个 PR 各自落地。
4. **一次 swarm 验证。** 完整 swarm 只在代码就绪的 head 运行一次。只有新行为、重新设计或大块新差异才再跑一次完整 swarm。变基、解决合并冲突或小修复在新 head 上只需单个验证者，纯措辞改动则不需要。按 **swarm** 技能在代码就绪的 SHA 上铺开独立验证者。它们重跑闸门，通过相应控制技能（如项目自带的 UI 或 CLI 测试装置）或指定的驱动在真实界面上实测承重行为，并审计差异。没有实况 lane，或者在你审计 merge-ready 报告的凭据之前，裁决都不算干净，因为任何 lane 都不信任它未检查过的声明。

   只在能证明问题时才阻塞 PR：head 上有失败的运行，或 PR 把某行文档改错了。PR 基线（无论主干还是堆栈中它下面的 PR）本就存在的问题不构成阻塞，除非该 PR 复制了它或新触及了它。只有用户会碰到的缺陷、失败的闸门、发错的文档才阻塞，其他一切进后续事项。
5. **所有者只合并你验证过的、并在其落地的主干上测过的内容。** 仅 CI 全绿绝不构成合并授权。swarm 的 lane 启动后，合并准备要变基到当前主干、报告新 head，并等待绿色 CI。

   合并前一刻，抓取主干并判断其改动是否影响该补丁，因为每来一次主干移动就变基永远没完。当将要落地的代码从未被测过时（例如冲突、双方都改的文件，或 PR 的检查集发生变化），要做变基并等 CI。双方都改动的 lockfile 若在合并结果上冻结安装通过、且 PR 改动的包在该结果上的解析与 head 一致，则无需变基，因为该安装测试的就是将要落地的 lockfile；若安装失败，则变基必须修复它。当主干改动了补丁的调用方或补丁依赖的东西（如它调用的代码或某个依赖版本），在合并结果上运行该补丁的检查，通过即合并。否则直接合并。如果主干会在合并准备之后第三次迫使变基，就停下并向根代理报告，由根代理为冲突的工作排序。
6. **运行根层。** 任何放宽闸门的操作（例如提高预算或加入 allowlist 条目）都需要验证者的证明，再加上你的重新会签，因为所有者才是想要全绿的一方。在覆盖审批的授权下，该会签就是审批，所有者对它的记录指向你的会签，供 lane 核查。被禁用或软失败的检查必须撤除，因为它不再守护任何情形。绝不要给出或绕过 forge 强制执行的审批，因为没有任何会签能覆盖它。

   操作者放行后，设定一个 1 小时的审计节奏并手动执行，持续审计到没有委派工作为止，因为长跑会漂移，代理会无声停滞。每个 tick 都从主干重读本剧本并修复漂移，例如未报告的 head 或未记录的代理，方式是让其所有者记录下来，因为漂移是记录中的缺口，而不是停滞。它探测每个代理，直至叶子 lane，并按副作用判断，因为状态文本和摘要可能掩盖卡住的子代理。代理出错、无法开始回合，或超过其 stuck-after 时长没有任何新动作，即为卡住；第一次 tick 时既未推送也未写轨迹行的所有者同样如此。正在等你或操作者的代理不算卡住，要去回答它。立即替换卡住的代理，不要等它的停止落地。给操作者带来变化的 tick，结束时按 **ketchup** 技能让其赶上进度；没有带来变化的 tick 保持安静。
7. **操作者叫停时立即停止。** 停工令以零写入命令的形式传达到每个所有者。各自报告所处位置，并保留其任务简报，直到操作者解除。

**回复：** 按 **ketchup** 技能让操作者赶上进度，覆盖每个 PR 的状态与裁决、合并了什么、会签及理由、尚未解除的操作者闸门、搁置的后续事项，并附上各 PR 与轨迹的链接。
