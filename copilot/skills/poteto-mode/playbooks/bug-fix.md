### Bug fix

**这个任务由你负责。规划、评审、验证。** 把调查和修复委派给子代理，自己保持在主导位置。按 Subagents 一节为每项工作选择子代理的推理级别以及快速或标准速度。

要讲科学。每一行上线的代码都能追溯到运行时证据。"可能有用"的多余保险措施只是假设，不是修复，不上线。当证据推翻某个假设时，回退由它引发的改动。只有证据支持的最小改动才上线，不多做。

1. 通过控制技能（Non-negotiables）在匹配界面上亲自复现，即使某个调试或埋点协议让你请用户去复现。只有在控制界面确实够不到目标、且你已把它推进到极限之后，才带着具体理由去问用户。如果无法直接复现，就合成触发条件、收紧条件，或加埋点到它触发为止。
2. 二分定位原因。列出候选假设，逐一排除直到剩下一个。用针对受影响子系统的 `how` 技能和 **why** 技能（查回归历史）为假设打底。每一轮取能砍掉最多剩余问题空间的划分，取得运行时证据，排除。程序状态不明时，加埋点或日志，在代码运行时读取。不要猜。用重复发送 `/lstack` 驱动漫长或顽固的排查。在第 3 步 architect/interrogate 铺开之前，用运行时证据确认幸存的*机制*。
3. 规划修复。若跨函数边界，先跑 `architect`。使用配置的 bug-fix 模型（模型文件记录了已确认标签时用该标签，否则用父模型）把实现委派给子代理，并给出具体范围。
4. 在同一界面上验证。原始复现现在通过。"不确定"或界面不对不算通过，要标记出来。单元测试展示的是分支行为，不是缺陷不存在。
5. 安排提交顺序，使失败的复现在 git 历史中先于修复落地。若缺陷有廉价的本地测试路径，按 **tdd** 技能采用先写失败测试的节奏。若测试昂贵、偏集成或不清晰则跳过。
   这是 **sequence-verifiable-units** 原则技能的典型应用：先写失败测试，再在其上修复。
6. 执行 **Opening a PR**。

**回复：** 坏在哪里、根因、修复、如何验证的。逐字粘贴先失败后通过的复现输出。
