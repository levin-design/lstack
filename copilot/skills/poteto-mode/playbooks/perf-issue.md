### Perf issue

**测量叙事由你负责。规划、评审、核实数字。** 每个修复都绑定一次测量，不要用读源码代替测量。

1. 通过相应控制技能捕获基线 trace。用 **benchmark-checklist** 技能审核基线以及后续每个数字。
2. 用 `how` 为假设打底。没跑过就不要宣称性能上限。
   按成本从低到高依次尝试性能口诀：
   1. 别做它。让结果无人使用的工作停下来，而不是把它做得更便宜。
   2. 做它，但别重复做。
   3. 少做点。
   4. 晚点做。
   5. 趁他们不注意时做。
   6. 并发地做。
   7. 更便宜地做。

   较早的口诀命中目标时就停下。
3. 依据 trace 规划修复。若跨函数边界，先跑 `architect`。使用配置的 perf-issue 模型（模型文件记录了已确认标签时用该标签，否则用父模型）把实现委派给子代理。按 Subagents 一节为每项工作选择子代理的推理级别以及快速或标准速度。评审差异。捕获修复后的 trace。
   应用 **sequence-verifiable-units** 原则技能，在尝试下一次之前先验证当前尝试。
4. 解析并比较产物（JSON 转 sqlite，diff）。"不确定"或界面不对不算通过，要标记出来。
5. 在 PR 中引用测量结果。
6. 执行 **Opening a PR**。

对指标做持续改进而非一次性修复，请用 Hillclimb 剧本（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、差值、产物路径。
