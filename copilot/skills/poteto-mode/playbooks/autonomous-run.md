### Autonomous run

**退出条件由你负责。先定义完成，然后不停顿地朝它推进。**

1. 在第一次迭代之前，把退出条件表述为可检查的谓词（测试全绿、复现已修复、全部 N 个 PR 已合并、像素差异为零）。
2. 选择唤醒机制。Copilot 没有 `/loop` 命令，因此长跑要依靠用户再发一条消息或重新调用 `/lstack` 来继续。把每次迭代设计成结束在一个用户可从中恢复的可检查检查点上。要监听的事件（CI、一次合并、ref 前进）交给一个观察者子代理，由它用一次调用汇报；没有事件可用时改用基于时间的检查。没有事件时，设一个固定间隔的心跳，间隔大小取决于结果何时值得重新检查。
3. 每次迭代只做证据支持的最小改动，对照谓词验证，有推进就提交，没帮助的改动就丢弃。那些"可能有用"的多余保险措施要回退，不要留着碰运气。
   通过 **sequence-verifiable-units** 原则技能安排工作顺序，在进入下一单元之前先验证当前单元，而不是把检查堆到最后。
4. 运行途中支持该目标的发现由你处理。通过 poteto-mode 自行处理损坏的技能、相关缺陷、不稳定的验证器、评审噪音、工具故障、被遗忘的后续事项，以及可修复的漂移。计划外的修复单独开 PR。不要把可逆的工作搁置给人类，也不要使用 `vscode_askQuestions`。只上报不可逆操作、没有实验能定论的真正产品或偏好决策，或真正的死路。以谓词为主要驱动力，每完成一项附带修复后回到它上面。
5. 每次迭代都通过 **show-me-your-work** 技能留检查点：一行记录改了什么、谓词是否移动。
6. 谓词满足时停止。平台期不是停止信号，要继续并转换方法推过去。真正的死路要上报而不是空转，绝不为了宣布胜利而放宽谓词。

**回复：** 退出条件、已运行迭代数、落地了什么、丢弃了什么、谓词最终状态。
