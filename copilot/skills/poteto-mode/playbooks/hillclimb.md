### Hillclimb

**指标与实验的完整性由你负责。监督并评审。把尝试委派出去。** 用于对单个可度量事物朝目标做持续的迭代改进。一次性修复属于 Bug fix 或 Perf issue。这里讲的是循环。

核心纪律：一次改动，一次测量，保留或回退。绝不叠加未测的改动，也绝不凭代码审阅宣称胜利（**prove-it-works** 原则技能）。

1. 选择指标之前，先落实工作负载和架构。对目标跑 **how** 技能，列出能影响结果的现实工作负载维度（数据规模、历史、状态、并发），并选一个能复现用户抱怨的用例。如果没有用例能复现，先修正复现，而不是开始爬坡。然后固定一个指标、一个"更好"的方向，以及一个可检查的停止谓词，把目标与尝试次数下限配成一对，使早期的幸运胜利无法结束运行（示例"至少比基线好 50% 且至少 10 次迭代"就是这个形态）。用户给了数字就用用户的，否则与用户商定。
2. 搭建测量装置，证明其灵敏度，然后冻结它（**build-the-lever** 原则技能）。运行对比鲜明的真实工作负载，确认目标用例复现症状，而更简单的用例按预期区分开。如果装置无法区分它们，就修改工作负载或指标。冻结之前用 **benchmark-checklist** 技能审核装置，并让它打印错误计数和工作量计数。冻结之后，用一条可重复的命令输出指标，采样充分以越过噪声（N 次的中位数，而非单次运行）。在任何改动之前，记录基线指标和回归闸门（必须持续通过的测试）的一次绿色运行。
3. 通过 **show-me-your-work** 技能开启决策日志。一个 `decision.tsv`，每次尝试一行：id、假设、改动、之前、之后、差值、测试、裁决（保留或回退）、备注。每次尝试前先读它。把它留在树外（gitignore）。
4. 把每个假设建立在第 1 步的架构模型上，使其指出具体机制（"把 X 移出启动路径，因为它在阻塞首屏"），而不是"试试给某处加 memoization"。对性能指标，按 Perf issue 剧本第 2 步中的性能口诀排序假设（`playbooks/perf-issue.md`）。只借用其顺序，不借用该步的停止规则。
5. 循环，每次迭代一个假设：
   - 使用配置的 hillclimb 模型（模型文件记录了已确认标签时用该标签，否则用父模型）把改动交给子代理，范围收紧。按 Subagents 一节为每项工作选择子代理的推理级别以及快速或标准速度。监督并评审差异，而不是自己敲（**guard-the-context-window** 原则技能）。当多个独立假设同时活跃时，把它们分给并行的子代理，各自在自己的工作树中（**separate-before-serializing-shared-state** 原则技能）。
   - 用冻结的装置测量改动前后，并运行回归闸门。
   - 只有指标越过噪声且闸门保持全绿才接受。否则完整回退该改动。"可能有用"的微调不保留。
   - 每个被接受的修复一个提交，只暂存你改过的文件（`git add <files>`，绝不用 `-A`）。无论保留还是回退，都记录该行。
   每次迭代在下一次开始前以一次检查收尾（**sequence-verifiable-units** 原则技能）。若运行无人值守，只借用 Autonomous run 剧本（`playbooks/autonomous-run.md`）的唤醒机制，不借用其停止规则。
6. 推过第一个平台期。遇到停滞、连续多次拒绝时，转换类别、组合接近的尝试、重读源码，或在断定爬坡完成前尝试更激进的方案。正确性和简洁性优先于数字。会破坏行为的胜利要回退；能保持数字的简化要保留（**laziness-protocol** 原则技能）。
7. 谓词满足时停止，或当剩余想法收益有限、不值其成本时停止。不要为了达标而放宽谓词，也不要在还有廉价未试假设时就放弃。如果卡住，上报而不是空转。
8. 按被接受提交的落地顺序堆叠，执行 **Opening a PR**。

**回复：** 指标与目标、基线到最终值及百分比差值、已运行迭代数（保留 vs 回退）、每个被接受的修复一行、`decision.tsv` 路径，以及如果继续推进你下一步会试的最佳想法。
