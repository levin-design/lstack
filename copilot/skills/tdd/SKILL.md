# TDD 缺陷修复

当修复缺陷且存在清晰、低成本的测试路径时，先让故障行为可执行，再改动生产代码。目标是写出一个聚焦的回归测试：它在修复前失败，在修复后通过。

当添加测试并不切实际时，不要强求。如果可用的测试需要大范围搭建测试装置、脆弱的 mock、缓慢的端到端基础设施、仅生产环境才有的状态、含糊的复现步骤，或大量无关的 fixture 改动，则跳过新增测试，改用最接近的有用验证方式。

## 工作流

1. **理解缺陷。** 确定预期行为、当前行为、受影响的路径，以及最小可观察的复现方式。
2. **选择最窄的可执行检查。** 优先使用该代码路径上已有的最接近的单元测试、组件测试、集成测试或回归测试。如果没有明显的实用测试路径，不要仅为了满足流程而从零创建一条。
3. **先写失败测试。** 添加能捕获该缺陷的最小、聚焦的测试。测试应编码预期行为，而不是镜像当前实现。
4. **修复前先运行新测试。** 确认它因预期原因失败。如果它通过，或因无关原因失败，则先修正测试或复现方式，再改动实现。
5. **修复缺陷。** 做出满足预期行为的最小生产代码改动，同时保持附近的契约不变。
6. **重新运行回归测试。** 确认测试现在通过。

## 当失败测试不切实际时

改用最接近的可执行回归检查：定向脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不加新测试，也不要加坏测试。坏测试指的是：大部分在测试 mock、编码了当前实现细节、依赖时序或无关的全局状态、为一个小修复需要昂贵的基础设施，或在证明修复有效后立刻会被删除的测试。

## 防护栏

- 不要为了让测试匹配错误实现而修改测试。
- 不要削弱已有断言，除非预期行为确实已改变且原因清晰。
- 让回归测试聚焦于该缺陷。避免大范围 fixture 改动或无关的覆盖率扩张。
- 如果缺陷是偶发的，尽可能让测试具有确定性，并记录被锁定的信号。
- 如果该缺陷暴露出更广的一类失败，先落地聚焦的回归路径，再考虑补充同类覆盖。

## 最终回复

报告证据，而不仅是结果：

- 指出修复前失败的测试或可执行检查，以及它产生的失败。
- 指出修复后通过的测试运行，以及所执行的附近验证。
- 如果无法展示修复前失败的证据，说明原因，并描述改用最接近的回归检查。
