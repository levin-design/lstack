# 为领域建模

把真实的领域编码进数据结构，而不是分散到各个条件分支里。与领域匹配的结构能让非法状态无法表示，并删除分支。在编写时选择它很便宜。事后再补回来会被视为重构并被不断推迟。

优先考虑：

- 用状态机代替散落的布尔值、阶段或生命周期检查。
- 用类型化模型代替松散的参数或重复的形状假设。
- 用映射、注册表、查找表或可判别联合代替分散在多个文件中的分支。
- 用 reducer 或命令/事件模型代替临时的状态变更。
- 围绕一块领域知识组织模块，而不是围绕“加载、校验、转换、保存”这样的顺序。执行顺序不等于归属。
- 用小的模块边界汇集重复的行为、归属关系或不变量。
- 在访问模式需要时使用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。当没有合适的结构时，先弄清代码绝不能允许什么、数据如何被读取，然后找到恰好编码这一点的结构。

不要强行套抽象。如果当前形态已经清晰、局部且不太可能增长，就优先选择无聊的代码。对只增加间接、却不消除分支、重复规则、非法状态或生命周期风险的抽象保持怀疑。

你跳过了这一步的迹象是：新功能让已有的 if/else 链又多了一个分支，或多了一个必须与第一个保持同步的布尔值。时间性分解是另一个迹象。以阶段命名的模块会在各步骤间重复同一套领域规则。
