# lstack 实用指南

适用：lstack 的 GitHub Copilot（VS Code）适配包。最后更新：2026-11-11。

这份指南回答四件事：装在哪、怎么触发、怎么并行、模型怎么配。

## 0. 一分钟心智模型

| 东西 | 是什么 | 谁读它 |
|---|---|---|
| Skill（`SKILL.md`） | 工作流知识、剧本、原则 | 你输入 `/name`，或 agent 按描述加载 |
| Agent（`.agent.md`） | 有工具权限和输出契约的角色 | 选择器选，或父 agent 派发 |
| Principle（`principle-*`） | 行为约束 | 被技能或 agent 正文引用 |
| Model config | “角色 → 模型”映射表 | 技能派发子代理前查表 |

四者互相独立：装技能 ≠ 建角色 ≠ 配模型 ≠ 约束行为。

## 1. 安装与目录

把包内容复制到项目根目录：

```bash
cp -R skills/. <project>/.github/skills/
cp agents/*.agent.md <project>/.github/agents/
```

装好后的结构：

```text
<project>/.github/
  skills/
    lstack/SKILL.md                       入口技能与技能地图
    lstack/references/lstack-models.md    模型配置（可选）
    <name>/SKILL.md                       58 个内置技能，各自独立注册
  agents/
    poteto-agent.agent.md                 通用委派子代理（可选）
    comment-sicko.agent.md                删注释评审子代理（可选）
    tech-lead.agent.md 等 9 个             通用数字员工（见附录 A）
```

说明：

- 每个技能都会独立注册，可以直接用 `/技能名` 调用。
- `agents/` 里的两个专用角色是 lstack 自带的；如不使用，可以删掉，但 `no-comments`、`swarm` 等技能会引用它们。
- 是否提交到 git 由项目决定；有些项目会把 `.github/skills` 和 `.github/agents` 加入 `.gitignore`，只在本机生效。

## 2. 三套入口怎么选

| 场景 | 入口 |
|---|---|
| 通用严谨工程任务 | `/lstack <任务>` |
| 只需要一个具体能力 | 直接 `/how`、`/architect`、`/tdd` 等 |
| 临时一批独立任务 | `/swarm` |
| 项目自定义的专用角色 | 在 agent 选择器里选对应的 lead |
| 不确定用哪个 | `/poteto-help` |

`/lstack` 会匹配 playbook，并按步骤调用其他技能。单点技能适合你已经明确知道要做什么的时候。

## 5. 并行机制与限制

能自动做的：

- 同一轮对话内，父代理可以在一个工具块里并行派发多个子代理。
- 全部返回后，父代理读取结果、丢弃不合格的、汇总成一份报告。
- `/swarm`（按切片覆盖）、`/arena`（同题竞速）、`/interrogate`（多视角审查）都建立在这套机制上。

不能自动做的：

| 限制 | 后果 |
|---|---|
| 子代理同步执行 | 不能后台跑，父代理必须等它返回 |
| 子代理无状态 | 看不到彼此，不能中途干预 |
| 跨轮不自动继续 | 这一轮结束就停，下一阶段要用户再发一句 |
| 无共享内存 | 协调只能靠父代理传话或落盘文件 |
| 写冲突 | 多个 worker 写同一文件会互相覆盖，必须隔离 |
| 层级受限 | 只有带 `agent` 工具的角色能再派子代理 |

实践建议：

- 一轮 2-5 个 worker 为宜。
- 每个任务书自包含：目标、范围、输入、输出、验证命令、报告格式。
- 每个 worker 有独立的输出目录或 worktree。
- 面板角色的列表长度 = 派发数量。

## 6. 模型配置

`/setup-lstack` 只做一件事：写 `.github/skills/lstack/references/lstack-models.md`。它不安装技能、不创建 agent、不约束行为。

配置发现顺序：

1. `.github/skills/lstack/references/lstack-models.md`（项目配置）
2. `~/.copilot/lstack-models.md`（用户级默认）
3. `~/.cursor/rules/pstack-models.mdc`（Cursor 旧配置，仅迁移）
4. 都没有：全部 `inherit-parent`

值：

| 值 | 作用 |
|---|---|
| `inherit-parent` | 派发时省略 `model`，用父对话模型 |
| 真实模型标签 | 该角色固定用这个模型 |
| 逗号分隔的列表 | 仅面板角色有效，每个条目派一个子代理 |
| `# budget: large (xhigh)` | 建议性推理强度，不改变具体角色 |

常见配置：

- 想让 Arena 跑 3 个候选：`arena runners: inherit-parent, inherit-parent, inherit-parent`
- 想让 Arena 有独立评审：`arena cross-judge pool: <与父模型不同系列的真实标签>`
- 全 `inherit-parent` 时：所有子代理用父模型，Arena 跳过交叉评审，`/swarm` 仍然扇出但模型一致。

零配置原则：默认就是全部 `inherit-parent`，不写文件也能用。只有需要按角色分配模型或启用 Arena 跨模型评审时，才值得配置。

## 7. 标准工作流

以“设计 → 实现 → 审查 → 测试”为例：

```text
阶段 0 勘查
   ↓ 用户确认 DoD 与现场条件
阶段 1 设计（多个设计子代理并行）
   ↓ 用户确认“契约冻结”
阶段 2 实现（多个实现子代理并行，写区隔离）
   ↓ 各自构建 + 单测通过，报 SHA
阶段 3 审查 + 验证（只读审查与独立验证同轮并行）
   ↓ BLOCKING 清单
阶段 4 修复复验（新 SHA 上全门禁重跑）
```

门禁规则：

- 契约没冻结，实现角色不得开工。
- 审查与验证必须针对同一 SHA。
- 修复产生新 SHA 后，受影响的构建、测试、审查全部重跑。
- 只有完成定义每一项都有证据，才宣布完成。

## 8. 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 选择器里只有某个 lead | 其他角色 `user-invocable: false` | 需要单独用时改成 `true` |
| 每次 setup 都重新问 | 调的是 Cursor 版技能，或项目文件不存在 | 使用项目文件，或不再运行 |
| agent 不出现 | VS Code 没打开对应工作区 | 打开项目并重载窗口 |
| Arena 没有评审 | 池里全是 `inherit-parent` | 填一个真实模型标签 |
| 子代理没并行 | 分在不同轮次，或有依赖 | 同一轮多次派发，或改串行 |
| 角色文件没进 git | `.gitignore` 忽略了 `.github/agents` | 需要共享就删掉该行 |
| `/swarm` 没自动执行 | `disable-model-invocation: true` | 必须由用户输入 `/swarm` |
| 切下一轮后技能丢了 | 普通回车只附着一条消息 | 每条消息重新选技能 |

## 附录 A：数字员工

`agents/` 提供一组通用岗位，不绑定具体项目。名册见 [agents/README.md](../agents/README.md)。

| 角色 | 工具边界 | 职责 |
|---|---|---|
| `tech-lead` | 全部 + `agent` | 总编排：勘查、冻结契约、并行派发、按证据验收 |
| `architect` | 只读 | 接口契约、模块边界、数据形状、权衡 |
| `frontend-engineer` | 读写 + 执行 | UI、组件、无障碍与浏览器行为 |
| `backend-engineer` | 读写 + 执行 | API、服务、数据与服务端安全 |
| `engineer` | 读写 + 执行 | 跨层或小型实现；无明确归属时兜底 |
| `ci-engineer` | 读写 + 执行 | 工程与运维：流水线、缓存、产物与发布自动化 |
| `reviewer` | 只读 | BLOCKING / NON-BLOCKING 审查 |
| `verifier` | 只读 + 执行 | 独立跑构建/测试/验收 |
| `writer` | 读写文档 | README、设计文档、PR 描述 |

`tech-lead` 是唯一默认可选的角色；其余 8 个通过 `user-invocable: false` 隐藏，由队长派发。需要单独使用时改成 `true`。

### 特化到具体项目

不要把项目路径、模块名、设备名写进通用 agent 文件。正确做法：

1. 任务书里给项目根目录、构建/测试命令、设计文档路径、验收标准。
2. 让 agent 先读项目根目录的 `AGENT.md`、`README.md`、设计文档。
3. 需要长期固定的项目角色时，复制一个通用文件，改 `name`、`description`、岗位边界和引用文档，放到项目的 `.github/agents/`；不要改通用版本。

### 启动提示词

```text
使用 tech-lead。
项目根：<绝对路径>
目标：<一句话>
范围：<目录/模块>
完成标准：<可验证的条件>
先做阶段 0 勘查，列出仓库地图、构建/测试命令、缺口和任务拆分。
等我确认后再进入设计，不要开始写代码。
```
