# 验证现有修复

当打开的 pull request 或已合并 commit 有可能修复该报告时，使用此模式。

现有制品拥有该修复。验证它。不要编辑它、编写竞争性补丁，或打开另一个 pull request。

## 判定制品资格

要求一个具体的制品：

- 打开的 pull request，其代码改动处理该症状
- 已合并的 pull request
- 已合并的 commit，其代码和意图与报告匹配

thread 中的声明、tracker 状态、分支名或原因假设，如果没有 pull request 或 commit，是不够的。

存在多个制品时，选择从 source thread 或 tracker 链接的那个。否则选择与受影响代码最接近的，并说明理由。

## 保护工作树

在仓库支持时，使用隔离的 worktree 或其他干净检出。不要覆盖用户的改动。

记录：

- 基线修订版本
- 打过补丁的修订版本
- pull request 或 commit URL
- 两次运行共享的构建和环境输入

使用常规的 `github.com` pull request 链接。

## 测量基线

对于打开的 pull request，使用其 base branch 作为基线。

对于已合并的修复，使用修复之前的那个修订版本——前提是该修订版本能构建并代表旧行为。

通过配置的 control adapter：

1. 启动基线应用。
2. 确认正确的应用和环境。
3. 通过真实 UI 操作运行报告路径。
4. 观察判别性症状。
5. 重置并重复一次。
6. 采集基线录像、截图和状态检查。

如果症状在基线上没有出现两次，就没有基线。不要声称修复有效。

## 测量打过补丁的构建

用相同的环境和数据构建并运行 pull request 或修复 commit。

1. 运行相同的 UI 路径。
2. 重复两次。
3. 确认损坏状态已消失。
4. 确认预期状态出现。
5. 采集修复后的录像、截图和相同的状态检查。

不要在编译或测试处止步。修复后结果必须来自正在运行且已打补丁的应用。

## 结果

### 已确认

基线复现两次，打过补丁的构建解决两次。

- 把 operations 状态标记为已验证。
- 链接该制品。
- 在 source preflight 之后发布一条简洁的 source-thread 回复。
- 包含前后对比结果。
- 不打开任何 pull request。

### 修复不足

症状在基线和打过补丁的构建上都出现。

- 把 operations 状态标记为已复现但未修复。
- 链接该制品并说明它未解决该症状。
- 如果本次运行尚未使用过正常的确认复现 source 更新，则发布它。
- 不打开竞争性的 pull request。

### 无结论

基线未复现、打过补丁的应用无法运行，或证据未展示判别性状态。

- 不要声称成功。
- 说明哪一半无法测量。
- 把结果保留在 operations thread 或运行输出中。
- 除非直接问题需要回答，否则不要在 source thread 中发布任何内容。

## 清理

停止两个构建，按保留策略移除临时配置文件和截图，并把仓库恢复到之前的状态，不得丢弃用户的工作。
